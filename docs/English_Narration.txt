Project goal
This video presents HR Ask, a policy question answering and ticket drafting prototype. Employees need to understand leave, attendance and social insurance procedures. HR staff repeatedly explain those policies and check incomplete requests. The project combines policy lookup with draft preparation. It uses fictional policies and synthetic employee information. This video presents actual application screenshots with synthetic English narration. It is not a continuous screen recording or the student's own voice.

How the system works
The system retrieves relevant sections from five fictional policy documents using term weighting and similarity. Rules and a language model distinguish consultation, drafting, clarification and escalation. OpenRouter provides access to the model, which answers using retrieved evidence. Python extracts and validates five ticket fields. The prototype implements retrieval, validation and evaluation locally, while renting language generation through an existing API. This avoids training a model from scratch, but introduces provider dependence and variable output quality. The local rules also cannot cover every possible expression.

Demo 1: policy consultation
The first question asks how many days of annual leave are available each year. The interface shows openrouter as the actual mode, indicating a real model response. The intent is consultation. The answer states that full time employees of this fictional company receive twelve days, and includes a source identifier. No ticket is generated. This is appropriate because the employee asked about policy rather than requesting a draft. The twelve day allowance is a simulated company rule, not a claim about employment law.

Demo 2: a complete ticket draft
The second request explicitly asks for annual leave and supplies an employee identifier, a date, a reason and a contact channel. The system identifies drafting intent. The five fields on the right match the request, including the annual leave type. The draft still requires human checking and has not been submitted or approved. However, the answer on the left unnecessarily asks for a name and other personal information. This conflicts with the complete draft status. It is a real limitation in the observed output: correct structured fields do not guarantee that the accompanying explanation is fully correct.

Demo 3: missing information
The third request simply asks for help correcting a missing attendance record. The request type is identified correctly, but the employee identifier, date, reason and contact channel are unknown. These four fields remain null, and the application asks the user to supply them. This avoids inventing employee information. It is successful handling of missing information, but it is not a complete ticket. In the current version, the user must include the full details in a new request to regenerate the draft.

Evaluation after the revised proposal
The revised proposal requires separate policy and ticket measures. In the saved live run, twenty five cases received real model responses and five were handled by local rules. After the prompt repair, all thirty automated engineering checks passed. However, a later AI assisted content review passed only twenty two of twenty five eligible policy answers. It identified an unnecessary name requirement, an overly absolute leave decision, and an unsupported generalization about contribution rates. This review was performed after observing the answers, not independently or before testing. Intent accuracy was thirty out of thirty, with three escalations and two clarifications. A new set of informal offline questions passed seven of twelve cases. The example, need leave tomorrow, family thing, was not handled as intended. These are important limitations, not results to conceal.

Interpreting the success metrics
The metrics need to be interpreted separately. All five cases with complete input produced complete tickets. All three cases with missing information preserved unknown fields and requested clarification. However, across all eight drafting cases, first turn completion was only sixty two point five percent. This remains below the original target of more than eighty five percent. Safe handling of an incomplete draft must not be counted as complete ticket generation. Likewise, passing thirty automated task checks does not replace the original business success criterion.

Limitations and next steps
The prototype demonstrates policy consultation, complete drafts and missing information handling. It still needs consistent answer wording, guided collection of missing fields, and better handling of informal requests. The revised proposal asks for expected answers before evaluation. The original live run did not satisfy that stronger procedure, and retrospective review cannot change this fact. Before a new model evaluation, freeze a separate test set and rubric, then obtain independent HR review. The report records observed API usage separately from hypothetical labour savings. No real productivity benefit or production deployment is claimed. AI tools assisted the code, report, review and this video. All drafts require human checking, and the assistant has no formal submission or approval capability. Thank you.
